# Architecture

## Current implementation

One `app` Gradle module with Kotlin and Compose. A launcher screen provides notification permission controls, persisted relay settings (master switch + explicit Telegram switch, both off by default, task 2.3), a test-relay-notification button, the Garmin Connect app-filtering guide and a Phase 0 debug section showing sanitized notification metadata captured by the listener. The manifest registers a notification listener guarded by Android's binding permission.

`RelayNotificationListener` records external posted/removed events (ignoring WristRelay itself) into a bounded in-memory store (`DebugEventStore`, max 50 entries, process-lifetime only). Each record is metadata-only: package, user, key, timing, ongoing flag and extra summaries that reduce string/char-sequence values to type and length. Message bodies, titles and sender names are never read into retained state; the store is not persisted or logged.

Prototype relay: for Telegram snapshots only (`org.telegram.messenger`, verified variant on a stock Android phone), `TelegramExtractor` reads the cumulative MessagingStyle `EXTRA_MESSAGES` array and `MessageTracker` diffs it against a bounded per-conversation cursor (count of already-relayed entries + timestamp of the newest relayed message; no stable per-message identity exists — verified 0.1). Growth emits the new positional slice. On shrink/repeat — including Telegram rebuilding the array from scratch, a verified device behavior that otherwise swallowed the first message of every series (owner repro 2026-10-13, VALIDATION.md) — entries are classified by per-message timestamp: strictly newer than the relaid watermark means genuinely new and is emitted; older-or-equal means already-relayed leftovers and collapses silently. Entries without timestamps keep the conservative "shrink = read" behavior. Known limitation: an offline-sent message arriving with an older timestamp is classified as already-relayed and stays silent. `TelegramRelayPipeline` binds tracking to a `RelayPublisher`; `RelayNotificationPublisher` (the production implementation) posts exactly one independent notification per genuinely new message with unique never-reused ids/tags; source Telegram notifications are never cancelled or modified. `onListenerConnected` establishes a silent baseline so reconnects never replay stale conversations. Since task 2.3 the relay gates live in `RelaySettings` (DataStore, settings only): master switch and explicit Telegram switch, both default off, mirrored synchronously for listener callbacks by `SettingsGate`; a settings collection re-baselines active notifications via `RelayActivationWatcher` the moment the relay turns on, so conversations that predate enabling are never replayed. Since task 2.2 the relay channel `wristrelay.relayed_messages_silent` is silent on the phone (IMPORTANCE_LOW, no sound) — watch mirroring of silent notifications remains a device-validation item (VALIDATION.md, 2.2/3.1); the loud task-0.2 prototype channel `wristrelay.relayed_messages` is left untouched because deleting a channel would cancel its active entries.

Task 2.1 parser variant handling (fixture-covered; see VALIDATION.md for what is not device-verified): per-message sender persons are kept per entry (group messages retain each sender), with the legacy plain-string `sender` bundle key accepted as a fallback; per-message `time` is carried on `RelayMessage.timestampMs` as delivered (permissions: `Long`/`Int` tolerated, missing yields null) and never used to re-sort messages — array order remains authoritative so out-of-order clock values cannot change positional identity. Entries with blank/absent text (media-only, redacted or stripped payloads) are skipped; a snapshot consisting only of such entries is unsupported (null). A snapshot without an `EXTRA_MESSAGES` array — e.g. a whole-conversation summary — is also unsupported and emitted as nothing; it is not treated as read evidence. Missing conversation title or group flag are tolerated as null/false. There is deliberately no `NotificationSource` abstraction yet: only one source is verified, and the package gate lives in `TelegramExtractor`.

## Intended pipeline

1. Listener receives Android posted/removed callbacks.
2. Source gate rejects WristRelay itself and all applications not explicitly enabled.
3. Telegram adapter extracts normalized messages and relevant snapshot metadata, ignoring inappropriate summaries.
4. Detector compares successive source states and identifies genuinely new messages.
5. Relay allocates unique active notification identities and publishes an independent entry per message.
6. Cleanup applies a policy validated against real removal/replacement behavior: there is no automatic cleanup (ADR-012, owner evidence R1–R3, 2026-10-13). Telegram notification removal is not read evidence and never triggers anything; relay entries persist until the user dismisses them or the system removes them, and those explicit user actions propagate to watch copies via mirroring.

Responsibilities can live in `listener`, `source/telegram`, `model`, `processing`, `relay`, `settings` and `ui` packages. Create implementations when needed rather than empty placeholder classes. No `NotificationSource` abstraction exists while only one source is verified; a shared interface will be extracted if and when a second verified source arrives. Detector APIs remain provisional until Phase 0 provides actual metadata.

## State and identity

Normalized messages need source package, conversation identity/title, sender, body, timestamp and optional source identity. Android does not guarantee Telegram message IDs. Snapshot order and multiplicity may matter when identities are absent; sender/body alone cannot distinguish legitimate repeated texts. Per-message timestamps (task 2.1) are display/order metadata only — they are never used to reorder or deduplicate, because positional array order is the sole identity signal.

Caches must be temporary and bounded. Settings — and only settings — are persistent (DataStore since task 2.3). Restarts/reconnections need a deliberate baseline policy to prevent stale replay; no message database is proposed. Enabling relay re-baselines whatever is already on screen before new messages relay (task 2.3).

Active relay notifications need unique IDs/tags that are not reused while active. New arrivals do not update previous entries. Channel/presentation choices are subject to Garmin acceptance. Automatic cleanup must not erase unread watch entries merely because Telegram replaced a source notification.

## Execution and dependencies

Use Android-managed listener callbacks, no polling or permanent foreground service. Filter early and keep callbacks short; move expensive work off the main thread if profiling requires it. Manual wiring is sufficient. Compose provides UI, DataStore will persist settings, JUnit and Android integration tooling verify behavior. No networking dependency is needed.
